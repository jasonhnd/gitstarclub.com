# gitstarclub SEO design

## Scope

This document defines the SEO rules for each page type (`title` / `description` / `canonical` / `robots`), the sitemap shard structure, the semantics of on-demand ISR in an SEO context, and the internal-link strategy. Generative answer-engine citation strategy, answer capsules, FAQ / Dataset schema, AI crawler hygiene, IndexNow, and GEO metrics are in [GEO.md](./GEO.md).

> SSG's core value is **indexable by search engines and shareable**. Target traffic (millions–tens of millions/day) comes mainly from search-engine long tail
> (such as `langchain star history`, `github trending 2024`, `vercel github stars`, `anthropic org star ranking`).
> **SEO is not a bonus, it is the premise on which the goal holds** — this site has no brand-term traffic and no social viral engine, and the only scaled customer acquisition is "every page precisely hits one long-tail query".
>
> Related documents: rendering / page layering / ISR see [ARCHITECTURE.md](./ARCHITECTURE.md); pages / URL / i18n / tone / palette see [PRODUCT.md](./PRODUCT.md);
> domain topology / Blob / environment variables see [OPS.md](./OPS.md). Technical facts are based on **Next.js 16.3.5** (App Router + Metadata API).
> AI answer-engine citation strategy is owned by [GEO.md](./GEO.md); this document stays focused on classic search crawl, canonical, metadata, sitemap, and internal-link mechanics.
> Performance targets are owned by [TESTING.md](./TESTING.md); the issue #25 measured Lighthouse / Core Web Vitals baseline is supporting evidence in [perf/CWV-25.md](./perf/CWV-25.md).
>
> i18n rollout definition: server-side multilingual URLs are already live (see [I18N.md](./I18N.md)). English stays unprefixed; ja/zh/zh-TW/ko/es/fr use prefixed URLs; page body, metadata, canonical, `hreflang` / `x-default`, sitemap, and language-switch navigation are all emitted according to route locale. The `gsc_lang` cookie is kept only as a preference-redirect signal for middleware / `/api/lang`, and does not participate in page rendering.

## 0. Core principles (read this first)

1. **Each page = one long-tail landing page**: the title must contain real search terms (`star history`, `trending`, year, repo / org name). A page is not "decorating displayed data"; it is "answering one specific query".
2. **Long tail uses on-demand ISR, but is still full server-side HTML**: history / repo / org pages are not built at deploy; on first visit they are generated by ISR — but what is generated is **complete server-rendered HTML**, indexable with no difference for crawlers and for prerendered SSG (see §3).
3. **sitemap is the long tail's only discovery entry**: on-demand ISR pages have no "natural backlinks" to feed crawlers, so **the sitemap must enumerate every URL**; otherwise crawlers can neither discover them nor ever trigger their generation. The sitemap and internal links jointly take on "making crawlers walk the whole site".
4. **Preview environments are always `noindex`**: the test environment runs on a Preview deployment of the same Vercel project (see [OPS.md](./OPS.md) deploy topology) — preview **must never be indexed**, otherwise `*.vercel.app` / `pre.gitstarclub.com` seize brand terms and cause duplicate content and confused domain ownership (see §11).
5. **Performance is a ranking factor**: SSG with zero client JS + HTML < 20KB naturally satisfies Core Web Vitals (see §12).

## 1. Indexing targets and page inventory

> ⚠️ **The page set (page-surface) is the working default**; entries marked `TBD PRODUCT` are product tradeoffs and may be adjusted, but **the data layer is fully budgeted and ready** (see the ARCHITECTURE data model), and the long tail uses on-demand ISR ⇒ the cost of "becoming a page" is extremely low and does not consume build budget, so page-surface can be opened up.

### 1.1 Page-type matrix

| Page type | URL pattern | Render tier | Scale (single language) | Indexing priority |
|---|---|---|---|---|
| Home | `/` | Core (deploy build) | 1 | Highest |
| Year page | `/rankings/2024` | Current-year core / historical on-demand ISR | ~11 | High |
| Month page | `/rankings/2024/10` | Current-month core / historical on-demand ISR | ~132 | High |
| Repo detail page | `/:owner/:name` | On-demand ISR | 5,300+ (the tracked set) | Medium (long-tail main force) |
| **Org detail page** | `/o/:login` | On-demand ISR | ~1,000s (including User+Org owner) | Medium (long-tail main force) |

| About page | `/about` | Core | 1 | Low (but needs indexing) |
| Week page | `/rankings/YYYY/W##` | Current-week core / historical on-demand ISR | ~570 | Medium |

> **locale indexing model**: the scale in the table above is the base canonical path cardinality. English uses unprefixed URLs; each non-default locale generates the same set of prefixed URLs (see §10), so the indexing-target URL count is about the base path count × 7.

### 1.2 Ranking matrix (data layer fully covered; becoming a page is a PRODUCT tradeoff)

Ranking = **{week / month / year / all-time} × {repo / org} × {flow=new / stock=total}**, all already budgeted into JSON in the pipeline (see the [ARCHITECTURE.md](./ARCHITECTURE.md) data model). **Presentation**:

| Dimension | Default presentation | Independent page? |
|---|---|---|
| **Weekly ranking** (week × repo/org × flow/stock) | **Independent week page `/rankings/YYYY/W##`** + a week-summary section inside month/year pages (links to the week page) | Already an independent page |
| **Monthly ranking / yearly ranking** (month/year × …) | Body of the month page / year page | Already an independent page |
| **Org ranking** (org dimension) | Org detail page `/o/:login` + an org section inside each period page | Org detail page is already independent |
| **All-time ranking** (all-time × repo/org × stock) | **Independent page `/rankings`** | Already an independent page |

> This matrix is **far more** than the old design's ~5,400 pages (a pure repo monthly chronicle): org pages may number in the thousands, the all-time ranking is independent, and the weekly ranking is independent. Shard math is estimated first from the base canonical path cardinality, then multiplied by 7 locale URLs (see §4 / §10).

### 1.3 Indexing-target magnitude (estimate)

| Dimension | Home | Year | Month | repo | org | rankings + about + compare | Subtotal of the table above |
|---|---|---|---|---|---|---|---|
| Base canonical path count | 1 | ~11 | ~132 | 5,300+ (the tracked set) | ~1,500 (est.) | ~3 | **~6,900** |

> The subtotal above, ~6,900, is the base canonical path cardinality, **not including week pages, `/pulse`, owner-index pagination, or category pagination**; after adding these crawlable entries, each locale sitemap is currently planned at about **~10k URL**, and total indexable URLs are about that base path list × 7. The exact count floats with the org whitelist (including User owners) and the category count.

## 2. Specification: title / description / canonical templates (one example for each page type)

**Global conventions**:

- `metadataBase = new URL(process.env.NEXT_PUBLIC_SITE_URL)` (see [OPS.md](./OPS.md), production = `https://gitstarclub.com`); all relative URLs are resolved to absolute URLs from this.
- The shared `web/app/_shell/RootShell.tsx` and the two route-group layouts set the site metadata base; each page uses `title` (a string) or `title.absolute` (the home page uses absolute, to avoid a duplicated suffix). Each page's metadata is built uniformly by the `pageMeta(...)` helper in `web/lib/seo.ts` (injecting `canonical` / `openGraph.url` / `twitter.images` / the default OG card).
- The root layout also emits `robots: { index, follow }` globally according to `SITE_INDEXABLE`: the default is `false` (noindex during the preview period); see §5 / §11.
- **Each page's canonical points at the current locale's own canonical URL**: English stays unprefixed, and non-default locales use a prefix; `pageMeta()` uniformly emits `hreflang` / `x-default` alternates (see §10).
- Titles contain **real search terms**: `star history` / `trending` / year / repo / org name / `ranking`. The description is ≤ 155 characters, contains numbers and concrete entities, and the first sentence is the value.

> Next.js 16 implementation: static pages use `export const metadata`; dynamic pages that depend on `params` use `export async function generateMetadata({ params })` (`params` is a Promise and must be `await`ed). Wrap JSON-view reads with React `cache()` so that `generateMetadata` and the page body **share the same data read** (deduped).

```ts
export async function generateMetadata({ params }: { params: Promise<{ year: string; period: string }> }): Promise<Metadata> {
  const { year, period } = await params;
  const week = /^W(\d{1,2})$/i.exec(period);
  const label = week ? `${year} Week ${Number(week[1])}` : `${monthLabel("en", Number(period), "long")} ${year}`;
  return pageMeta({
    title: `${label} GitHub Star Rankings`,
    description: `GitHub repositories ranked by stars gained in ${label}.`,
    path: `/rankings/${year}/${period}`,
    locale: "en",
    ogImage: `/rankings/${year}/${period}/opengraph-image`,
  });
}
```

- Terms included: the full English month name (`October 2024`) / the week number (`2024 Week 41`), `GitHub Star Rankings`. **Months use the full English name** (search volume is higher than the numeric `2024/10`).
- The weekly ranking is an **independent page** (`/rankings/YYYY/W##`); the month page no longer embeds a week section. Month pages / year pages point to week pages through internal links (see §9).

### 2.4 Repo detail page `/:owner/:name`

Actual implementation (English adapter `web/app/(en)/[locale]/[owner]/page.tsx`, localized adapter `web/app/(localized)/[locale]/[owner]/[name]/page.tsx`, shared `web/app/_localized/repo.tsx`):

| Field | Template (`anthropics/claude-code`, entity found) |
|---|---|
| title | `anthropics/claude-code — Star History & Timeline` |
| description | `Star history for anthropics/claude-code: 98,432 stars. Growth curve, exact 10k/50k/100k milestones, monthly star gains, and ranking history.` |
| canonical | `/anthropics/claude-code` |
| ogImage | `/anthropics/claude-code/opengraph-image` (curve + numbers + repo name drawn live per repo) |

```ts
export async function generateMetadata({ params }: { params: Promise<{ owner: string; name: string }> }): Promise<Metadata> {
  const { owner, name } = await params;
  const fullName = `${decodeURIComponent(owner)}/${decodeURIComponent(name)}`;
  const id = (await getRepoIdByFullName()).get(fullName.toLowerCase());
  const repo = id !== undefined ? await getRepoEntity(id) : null;
  // When not found, still return metadata (description falls back to fullName); the body then calls notFound() (see §3.2)
  if (!repo) return pageMeta({ title: `${fullName} — Star History`, description: `GitHub star history for ${fullName}.`, path: `/${fullName}`, locale: "en" });
  return pageMeta({
    title: `${repo.full_name} — Star History & Timeline`,
    description: `Star history for ${repo.full_name}: ${repo.current_stars.toLocaleString()} stars. Growth curve, exact 10k/50k/100k milestones, monthly star gains, and ranking history.`,
    path: `/${repo.full_name}`,
    locale: "en",
    ogImage: `/${repo.full_name}/opengraph-image`,
  });
}
```

- **The repo name is the strongest search term**: users search `<repo> star history` directly. The title puts `owner/name` first.
- `current_stars` uses `toLocaleString()` to add thousands separators (no "as of" date — a date is not hard-coded into the description for now, to avoid rewriting the description every day in a cold month).
- **Rename / migration**: the URL uses the current `full_name`; the old URL does a **308 permanent redirect** (see [PRODUCT.md](./PRODUCT.md) repo identity) → canonical always points at the current canonical URL, avoiding duplicate content.
- **Unknown repo**: `generateMetadata` returns fallback meta (`title = '<fullName> — Star History'`), and the page body calls `notFound()` to trigger the 404 UI + status code (see §3.2).

## 3. SEO semantics of on-demand ISR (this site's most critical SEO detail)

> UI chrome and the page body are server-rendered by route locale, and the build route table stays `○` (static) / `●` (on-demand ISR); there is no `ƒ` (force-dynamic). See [FRONTEND.md](./FRONTEND.md) §2.5 (render mode: route locale + server-side localized HTML). **The key implication for SEO**: each locale URL emits **complete indexable HTML** in the corresponding language (§3.1a), and the ISR persistent cache / CDN jointly carry the load.

**Render model** (see [ARCHITECTURE.md](./ARCHITECTURE.md) page layering): deploy builds only the **small core** (home / current year / current month / all-time ranking, plus the hot surfaces of the corresponding locales); history / repo / org pages are **on-demand ISR** — `dynamicParams = true` and `generateStaticParams` returns empty (or only the current year/current month) ⇒ they are not fully built at deploy; on first visit they are generated by route locale, stored in the Vercel persistent ISR store, and later hits are served from cache.

### 3.1 Four SEO implications that must be carried out

| # | Implication | How it is carried out |
|---|---|---|
| (a) | **An ISR page is still complete server-side HTML ⇒ fully crawlable and indexable** | Content pages have zero client JS, and charts are server-side SVG; a crawler's first fetch already gets the full HTML, **with no difference** from prerendered SSG. **The body does not depend on client JS to render**. |
| (b) | **The sitemap must enumerate all of these URLs** | Otherwise crawlers **cannot discover** long-tail pages and thus **never trigger** their generation. The sitemap is the on-demand ISR long tail's **only discovery entry** (see §4). Internal links are supplementary (see §9). |
| (c) | **After deploy the ISR store resets ⇒ the first crawler/visitor hit triggers regeneration** (acceptable) | One regeneration is a lightweight Function (it reads KB-scale JSON views and does not touch Parquet/the engine); under millions–tens of millions/day of traffic the cold-start share is negligible. **Deploy frequency is low** (only code/structure changes); data updates go through `revalidatePath` and do not reset (see ARCHITECTURE / OPS). |
| (d) | **Status codes must be correct + `lastModified` must be stable** | See §3.2 / §3.3. |

### 3.2 Status codes (correctness of crawler signals)

- **Valid param → 200**: `generateMetadata` / the page renders normally.
- **Unknown param → 404**: `getRepoEntity` / `getOrgEntity` finds nothing → call `notFound()` (Next.js returns 404 + the not-found UI). **Never return a 200 soft 404 for an unknown repo/org** (Google will judge it a "soft 404", waste crawl budget, and pollute indexing).
- **Renamed old URL → 308 permanent redirect**: permanently redirect to the current `full_name` (see [PRODUCT.md](./PRODUCT.md)) (the repo route is implemented from `lookup/aliases.json`, see [FRONTEND.md](./FRONTEND.md)).

```ts
// On-demand ISR segment config (repo / org / historical year-month)
export const dynamicParams = true            // Default; params not listed in generateStaticParams are generated on first visit
export async function generateStaticParams() {
  return []                                  // Long tail: not built at deploy, all generated on demand
}
// Note: returning [] requires cacheComponents off (when on, an empty array errors at build, see §3.4)
```

> Core pages (home/current year/current month/all-time ranking), in their own segments, have `generateStaticParams` return **concrete params** (the current year, the current month, `/rankings`) and are prerendered at deploy.

### 3.3 `lastModified` rules (used for both the sitemap and potential HTTP headers)

**Target state** (after sharding is implemented, see §4.4):

| Page | `lastModified` value | Stability |
|---|---|---|
| Historical year / historical month (already folded into the canonical shard) | The date that period's data was **last recomputed** (it changes only when a Vercel Workflow recomputes and publishes a new version) → effectively **fixed** | High (crawlers recrawl less often based on this) |
| Current year / current month / home / all-time ranking | **The most recent daily sync time** (`hot-snapshot` write time / UTC day) | Changes daily (crawlers recrawl diligently based on this) |
| repo / org detail | The date that entity **most recently had a data change** (on the ranking this month → daily granularity; long dormant → fixed at the last active month) | Depends on activity |

- **Stability principle**: a historical page's `lastModified` **must not jitter on every build** (otherwise crawlers misjudge the whole site as fully changed every day and waste budget). The value comes from **deterministic fields in the data view** (`updated_at` / the period-end date written by the pipeline), not `new Date()`.
- Same source as the §4 sitemap `lastModified` (the same field), so the sitemap and the page declaration stay consistent.

**Current state**: the sitemap has been changed to a `/sitemap.xml` index + 7 per-locale XML route handlers; `lastModified` is still derived by URL type from real data dates (see §4.2): historical year/month/week take the corresponding period-end date, capped by the published-data time; category paths take the registry `generated_at`; repo / org / core pages take `meta.backfilled_at` / `meta.generated_at` of the currently published view. The current lookup contract has no repo/org entity-level `updated_at`, so repo/org cannot yet express "that entity's last active day"; if that field is added to the contract later, tighten it to the entity-level date.

### 3.4 Configuration points (aligned with ARCHITECTURE)

- **`cacheComponents` off**: turning it on changes the `dynamicParams` / empty-array semantics (an empty `generateStaticParams` errors at build and needs a placeholder param — which conflicts with our "long tail fully on demand"). The MVP **keeps it off**.
- Long-tail segments `revalidate = false`: no time-based polling invalidation; only point invalidation via `revalidatePath` after a Vercel Workflow recomputes and publishes (a base data view changes only when a Workflow publishes a new version).
- **Hot set ISR reads only the KB-scale `hot-snapshot.json`**: never load Parquet / DuckDB / the engine on the request path (see ARCHITECTURE).
- **Streaming metadata**: for **crawlers that can execute JS** (such as Googlebot), Next.js 16 streams `generateMetadata` into the DOM, and Google can parse it correctly; for **HTML-limited crawlers** (`facebookexternalhit` / `Slackbot` / `Bingbot` / `Twitterbot`) it **blocks rendering and puts meta into `<head>`**. Our `generateMetadata` does not depend on runtime data (it only reads already-budgeted JSON) and can be prerendered into the initial HTML, so **both social fetches and search engines get a complete head**. There is no need to change `htmlLimitedBots`.

## 4. sitemap: sitemap index + per-locale XML (about ~10k URL per locale)

> **Sitemap protocol hard limit**: a single file ≤ **50,000 URL** and ≤ **50MB (uncompressed)**. The current sitemap is split by locale into 7 files; each locale file is about ~10k URL, under the single-file cap, and the total URL volume is about the base canonical path count × 7.

### 4.1 Current implementation (explicit XML route handlers)

Actual entries:

```txt
/sitemap.xml       -> web/app/sitemap.xml/route.ts
/sitemap-en.xml    -> web/app/sitemap-en.xml/route.ts
/sitemap-ja.xml    -> web/app/sitemap-ja.xml/route.ts
/sitemap-zh.xml    -> web/app/sitemap-zh.xml/route.ts
/sitemap-zh-TW.xml -> web/app/sitemap-zh-TW.xml/route.ts
/sitemap-ko.xml    -> web/app/sitemap-ko.xml/route.ts
/sitemap-es.xml    -> web/app/sitemap-es.xml/route.ts
/sitemap-fr.xml    -> web/app/sitemap-fr.xml/route.ts
```

Characteristics:

- `/sitemap.xml` is the sitemap index and lists the 7 locale sitemap files.
- Each locale sitemap enumerates the same set of canonical paths: English emits unprefixed URLs, and non-default locales emit prefixed URLs for `/ja`, `/zh`, `/zh-TW`, `/ko`, `/es`, and `/fr`.
- Every `<url>` carries a complete `xhtml:link rel="alternate"` set, including itself, the other locales, and `x-default` -> the English unprefixed URL.
- Covered paths: home `/`, `/pulse`, `/rankings`, `/compare`, `/categories`, `/about`, each year `/rankings/YYYY`, each month of each year `/rankings/YYYY/MM`, valid ISO week pages `/rankings/YYYY/W##`, all repos `/{owner}/{name}`, the `/o` org index and `/o/page/[page]`, all orgs `/o/{login}`, plus the public category paths and category pagination paths marked in `lookup/categories.json`; categories with an explicit `sitemap: false` are not enumerated.
- Path enumeration, locale URLs, alternates, `lastModified`, `changeFrequency`, `priority`, and XML serialization are all centralized in `web/lib/sitemap.ts`; route-handler data reads are in `web/lib/sitemap-routes.ts`, and the read cache is 86400 seconds.

### 4.2 Current `lastModified` values

```ts
return paths.map((p) => ({
  url: `${BASE}${p}`,
  lastModified: sitemapLastModified(p, { meta, categories }),
  changeFrequency: sitemapChangeFrequency(p),
  priority: sitemapPriority(p),
}));
```

- **Base data date**: `resolveSitemapLastModified(meta)` still resolves `meta.backfilled_at` (bootstrap) → `meta.generated_at` (versioned workflow meta) → the fixed fallback `2026-06-04T00:00:00.000Z`. The fallback is used only on abnormal paths; a normal publish uses the real meta time.
- **rank history pages**: `/rankings/YYYY`, `/rankings/YYYY/MM`, and `/rankings/YYYY/W##` take the last day of that year / month / ISO period, capped by the base data date, so that a future period or a not-yet-published data date does not enter the sitemap.
- **category paths**: `/categories*` takes `generated_at` from `lookup/categories.json`; if it is missing or invalid, fall back to the base data date.
- **repo / org / core pages**: the current lookup and entity contract do not expose an entity-level `updated_at`, so these URLs use the base data date of the currently published view; this is a real published-data date, more accurate than a hardcoded fallback, but it is not the last active day.
- **Do not fall back to `new Date()`**: when meta is missing or the timestamp is invalid, also use the fixed fallback, to avoid jitter on every build and to avoid misleading crawlers into judging that the whole site changed.

### 4.3 Future shard structure (implement when the scale approaches 50k)

Next.js 16 `app/.../sitemap.ts`'s `generateSitemaps()` returns `[{ id }]`, and shard output URLs are **`/<route>/sitemap/<id>.xml`** (v16: `id` in the default export is a Promise and needs `await props.id`). Plan:

```text
/sitemap.xml                          # sitemap index (Next.js automatically aggregates the shards below)
  /sitemap/pages.xml                  # Static/core: home + all-time ranking + about + /pulse + /compare
  /year/sitemap/0.xml                 # Year pages
  /month/sitemap/0.xml                # Month pages
  /r/sitemap/0.xml … /r/sitemap/N.xml # repo: each shard ≤ 50,000
  /o/sitemap/0.xml … /o/sitemap/M.xml # org
  /week/sitemap/0.xml                 # Independent week pages
```

```ts
// app/r/sitemap.ts — repo shard example (future)
import type { MetadataRoute } from "next";

const PER = 50_000;
const BASE = process.env.NEXT_PUBLIC_SITE_URL!;

export async function generateSitemaps() {
  const total = await countRepos();
  const shards = Math.ceil(total / PER);
  return Array.from({ length: shards }, (_, id) => ({ id }));
}

export default async function sitemap(props: { id: Promise<string> }): Promise<MetadataRoute.Sitemap> {
  const id = Number(await props.id);
  const repos = await getRepoSlice(id * PER, PER);
  return repos.map((r) => ({
    url: `${BASE}/${r.full_name}`,
    lastModified: r.updatedAt,
    changeFrequency: r.active ? "daily" : "yearly",
    priority: r.active ? 0.7 : 0.4,
  }));
}
```

### 4.4 `lastModified` / `changeFrequency` / `priority` rules when sharding is implemented

| Shard | lastModified | changeFrequency | priority |
|---|---|---|---|
| pages (home/all-time ranking) | Most recent daily sync time | `daily` | 1.0 / 0.9 |
| year (current year) | Most recent sync | `daily` | 0.8 |
| year (historical) | Fixed period-end date | `yearly` | 0.6 |
| month (current month) | Most recent sync | `daily` | 0.8 |
| month (historical) | Fixed end-of-that-month date | `monthly` | 0.6 |
| repo (active on the ranking) | Entity's most recent change date | `weekly`~`daily` | 0.7 |
| repo (dormant) | Last active month | `yearly` | 0.4 |
| org | Same logic as repo | `weekly`/`yearly` | 0.6 / 0.4 |
| about | Copy-change date | `yearly` | 0.3 |

- **Emit locale alternates**: every `<url>` contains the complete `xhtml:link rel="alternate"` matrix; `x-default` always points at the English unprefixed URL (see §10 and [I18N.md](./I18N.md)).
- **The sitemap itself is a Route Handler and is cached by default**: unless a request-time API is used. Our sitemap only reads already-budgeted JSON and can be statically cached; after a Vercel Workflow recomputes and publishes, a refresh via `revalidatePath` / deploy is enough.
- **priority/changeFrequency are weak signals**: Google basically ignores `priority`, and `changeFrequency` is only a hint; **what really decides recrawl is `lastModified` + actual content change** — so the stability in §3.3 is the most critical.

### 4.5 Known gaps in the current sitemap

| Item | Current state | Impact | Handling |
|---|---|---|---|
| repo / org entity-level active date | The lookup contract does not expose it | repo/org can still only use the published-data date and cannot express the last active day | If GSC shows wasted crawl budget, then add an entity-level `updated_at` to the data contract and wire it into the sitemap |
| `meta` missing or timestamp invalid | Abnormal path | A fixed fallback is already used, so the sitemap does not jitter per build | If GSC shows the fallback is too old and hurts discovery, then switch to hard-fail or an explicit env date |

## 5. robots.txt

For Cloudflare, run the owner commands in [OPS.md](./OPS.md) from `web/`. The production build needs `BLOB_BASE_URL` and `NEXT_PUBLIC_BLOB_BASE_URL` exported to the public store base before `bun run cf:build:production`. The production deploy uses an explicit empty Wrangler environment (`--env=""`) plus `--var CF_PREVIEW_COMMIT_SHA`. Do not omit the empty environment.

Build each target immediately before its deployment because the output directory is shared. The underlying commands are `bun run cf:build --site-target=production` and `bun run cf:build --site-target=pre`; a bare build fails. The production build embeds `SITE_INDEXABLE=1` and `NEXT_PUBLIC_SITE_URL=https://gitstarclub.com`; the production Worker declares the same runtime values. `bun run cf:dry-run` builds pre with indexing disabled and performs only a Wrangler dry run. The build checks generated home HTML and robots output. After the owner manually deploys each build, verify that production `/robots.txt` allows `/` and lists the sitemap, production home HTML has no `noindex`, and preview `/robots.txt` and home HTML remain blocked. The owner then resubmits the production sitemap in Google Search Console and Bing Webmaster Tools.

Generated with Next.js 16 `app/robots.ts` (`MetadataRoute.Robots`). **Actual mechanism: the environment variable `SITE_INDEXABLE` is the master switch** — not split by host; env decides whether indexing is opened. During the preview period (the teaser occupies the domain, and a private preview deployment runs the web app), even if the host is the production domain, as long as `SITE_INDEXABLE` is unset it returns `Disallow: /`, and the switch is flipped only on launch day:

```ts
// app/robots.ts (actual implementation, simplified)
import type { MetadataRoute } from "next";

const BASE = process.env.NEXT_PUBLIC_SITE_URL ?? "https://gitstarclub.com";
const indexable = process.env.SITE_INDEXABLE === "1";

export default function robots(): MetadataRoute.Robots {
  if (!indexable) return { rules: [{ userAgent: "*", disallow: "/" }] };
  return {
    rules: [{ userAgent: "*", allow: "/", disallow: ["/api/"] }],
    sitemap: `${BASE}/sitemap.xml`,
    host: BASE,
  };
}
```

Output (after launch, `SITE_INDEXABLE=1` is set):

```txt
User-Agent: *
Allow: /
Disallow: /api/

Sitemap: https://gitstarclub.com/sitemap.xml
Host: https://gitstarclub.com
```

Output (pre-launch, `SITE_INDEXABLE` unset or not `"1"`):

```txt
User-Agent: *
Disallow: /
```

- **Master switch = environment variable, not host**: this is the key difference from the early design. The original idea was that `isProductionHost()` would decide automatically by host / `VERCEL_ENV`, but the actual implementation chose the more robust **launch flag**: during the preview stage, even a Preview deployment on the production domain (the web app) stays silent, to avoid being exposed ahead of the teaser.
- **Launch flip procedure**: ① add `SITE_INDEXABLE=1` in the Vercel project's production environment ② redeploy (no code change needed) ③ `robots.txt` opens immediately + the sitemap is exposed + the root layout's global `robots: { index: true, follow: true }` flip together.
- **Do not block any content page**: each locale's roughly ~10k URLs all need to be crawled; crawl budget is digested jointly by the stable `lastModified` in §3.3 + the internal-link structure in §9 + the per-locale sitemap shards.
- **Block `/api/`**: cron / internal routes should not be crawled (the real defense is `CRON_SECRET` auth, see [OPS.md](./OPS.md); robots only reduces noise).
- **`/search-index` and `/repo-curve` (top-level JSON endpoints) are intentionally allowed**: neither is under `/api/`, so `Disallow: /api/` does not cover them. Both endpoint contracts are in [API.md](./API.md); `robots.ts` only does `Disallow: /api/` and does not block these two (CDN JSON, not content pages, harmless to SEO). If crawlers need to be stopped from fetching this JSON, add `/search-index` and `/repo-curve` to Disallow in `robots.ts`.
- **Handling of Preview deployments**: Preview has `SITE_INDEXABLE` unset by default → `Disallow: /`; on top of that, the root layout's `robots: { index: false, follow: false }` meta (driven by the same master switch) defends the same place. Preview must also set Deployment Protection (PRIVATE) on the Vercel project; see §11.
- The `host` field declares the canonical host (a few crawlers use it as a hint for consolidating mirrors).

## 7. canonical dedup strategy (overlapping ranking views)

The ranking matrix has a duplicate-content risk in which **multiple views point at the same set of entities**. Rules:

| Risk scenario | Strategy |
|---|---|
| The "week section" of the same ranking appears on both the month page and the year page | The weekly ranking by default **is not an independent page** (no independent URL ⇒ no duplicate URL); if the §1 week page is independent, then the week section inside month/year pages is only a summary + a link to the week page, **the week page's canonical points at itself**, and month/year pages do **not** canonicalize to the week page. |
| The repo view vs the org view of `/rankings` (if made as `?metric=` / a subpath) | **Pick one as canonical**: either show them side by side inside a single page (one URL, no duplication); or `/rankings` (repo, canonical) + `/rankings/org` (org, **canonical points at itself**, because the content really differs). **Never** let pure sort/filter queries such as `?sort=` or `?period=` produce indexable duplicate URLs — such URLs always canonicalize back to the parameterless canonical page. |
| Old and new URLs from a repo rename | Old URL **308** → new URL; canonical is always the current `full_name` (see §2.4 / [PRODUCT.md](./PRODUCT.md)). |
| Language versions | English is unprefixed, and non-default locales use prefixed URLs; all locale URLs of the same canonical path point at each other through hreflang, and `x-default` points at English. |
| Trailing slash / case | Uniformly **no trailing slash + owner/name keeps GitHub's original case**; other forms 301 to the canonical form. |

> Principle: **one piece of content, one canonical URL**. Query-parameter views (sort/filter/pagination excepted) all canonicalize back to the canonical page; views whose content really differs (org vs repo, different periods) each canonicalize to themselves.

## 8. Pagination (rel / canonical for long rankings)

If long lists such as the all-time ranking / yearly TOP are paginated:

- **The MVP prefers "a single page + a server-rendered list that is long enough"** (such as top 100) and **does not paginate** ⇒ there is no pagination SEO complexity, and with zero client JS there is also no "load more". This is the default.
- If pagination is truly needed (such as a full org list):
  - Each page `?page=2` has its **canonical pointing at itself** (not canonical back to page 1 — Google has deprecated `rel=next/prev` as an indexing signal, and canonicalizing back to the first page would drop deep-page content).
  - Optionally keep `<link rel="next">` / `<link rel="prev">` (a weak hint, harmless).
  - Paginated pages are `robots: index,follow` (so deep-page entity links get discovered); but **the first page (page=1) is that list's canonical entry**, and paginated-page titles add ` — Page 2` to distinguish them and avoid duplicate titles.
  - **Paginated URLs must also enter the sitemap** (otherwise deep-page entities cannot be discovered).

> Because this site's long-tail main force is repo/org **detail pages** (each an independent URL, discovered both by ranking internal links and by the sitemap), whether a ranking page is paginated has little effect on indexing — **prefer not to paginate**.

## 9. Internal-link graph (the key to crawlers digesting ~10k pages, together with the sitemap)

> Goal: **any page is reachable in ≤ 3 hops**; besides the sitemap, on-demand ISR pages can also be discovered by internal links / have their generation triggered. Internal links are "the channeling of crawl budget", the sitemap is "the full inventory", and neither can be missing.

```text
Home /
 ├─ Year spine (2015…current) ──────────────→ each year page /rankings/YYYY (1 hop to any year)
 ├─ This month's focus TOP / growth rate ──→ repo detail page /:owner/:name (1 hop to hot repos)
 ├─ On this day in history (milestones) ───→ repo / the corresponding month page
 ├─ All-time ranking entry ────────────────→ /rankings
 └─ Footer ─────────────────────────────→ /categories / /o

Year page /rankings/YYYY
 ├─ 12 month cells ────────────────────────→ month page /rankings/YYYY/MM (1 hop to any month)
 ├─ Yearly TOP rows (repo name) ───────────→ repo detail page /:owner/:name
 ├─ Leading-row public categories ─────────→ /categories/{dimension}/{slug} (registry public)
 └─ Complete ranking anchor ───────────────→ full ranking on the same page

Month page /rankings/YYYY/MM
 ├─ Repo name on each row of the three rankings → repo detail page /:owner/:name
 ├─ Leading-row public categories ─────────→ /categories/{dimension}/{slug} (registry public)
 └─ Complete ranking anchor ───────────────→ full flow ranking on the same page

Repo detail page /:owner/:name
 ├─ Milestones (frozen crossed_10k/50k/100k) → corresponding month page /rankings/YYYY/MM (if earlier than 2015 or later than the current UTC month, display only and do not link)
 ├─ Monthly performance table (recent N months, each row) → corresponding month page
 ├─ owner link ───────────────────────────→ org detail page /o/owner    (repo↔org cross-link)
 ├─ category links ───────────────────────→ the language / topic category it belongs to
 ├─ related repositories ─────────────────→ repos of the same owner or the same primary language
 └─ Rank history ─────────────────────────→ the corresponding period page

Org detail page /o/login
 ├─ top repo list (each row) ─────────────→ repo detail page /login/:name (org→repo)
 ├─ Member public-category chips ─────────→ /categories/{dimension}/{slug} (registry public + member assignments)
 ├─ Compare hot members ──────────────────→ /compare?repos= (at most 5 members by current stars)
 ├─ Monthly org performance ──────────────→ corresponding month page
 └─ All-time org rank / rank history (if the entity has rank_history) → /rankings or /rankings/YYYY/MM

Org index /o and /o/page/N
 ├─ owner on each row ────────────────────→ org detail page /o/login
 └─ prev/next + page numbers ─────────────→ pagination of all owners

All-time ranking /rankings
 ├─ Each row of the repo ranking ─────────→ repo detail page
 └─ Each row of the org ranking ──────────→ org detail page

Category detail /categories/dimension/slug
 ├─ repo on each row ─────────────────────→ repo detail page
 ├─ prev/next + page numbers ─────────────→ category deep pagination
 ├─ Browse all anchor ────────────────────→ same-page pagination
 └─ related categories ───────────────────→ other categories in the same dimension
```

**Key edges (must be implemented)**:

| Edge | Role |
|---|---|
| Year spine (home → each year) | All year pages are reachable in 1 hop |
| Month cells (year → each month) | Any month is ≤ 2 hops |
| Ranking row → entity (repo/org) | Long-tail detail pages are discovered + ISR is triggered; **this is the main discovery path for repo/org pages** |
| Milestones / monthly table → month page | Repo pages feed month pages back and form a mesh loop |
| repo ↔ org cross-links (the owner field) | Org pages are discovered from repo pages, and vice versa |
| repo → category / related repositories | The repo long tail feeds topic pages and similar repos back, reducing discovery by the sitemap alone |
| `/o` paginated index → org | Every owner has at least one crawlable in-site inbound link, reducing sitemap-only islands |
| Category-detail pagination → repo | category members 101+ get an inbound link from the topic hub page, and the page 1 canonical is not broken |
| rankings full-ranking anchor | Rank rows outside the top slice of year/month/week detail pages can also be discovered on the same page |
| Footer → `/categories` / `/o` | Every page on the site provides category and owner directory entries |
| prev/next (previous/next month, previous/next year) | The timeline connects horizontally, reducing islands |
| Breadcrumbs (§6.7) | Each page links back upward, connecting vertically |

- **Depth check**: home→year (1)→month (2)→repo (3) = 3 hops; home→all-time ranking (1)→repo (2); home→hot repo (1)→owner org (2); any page→Footer `/o` (1)→any org (2+pagination); any page→Footer `/categories` (1)→category (2)→category-pagination repo (3+pagination). The core long-tail entries are achieved.
- **Island risk**: a repo/org that has long been dormant and has never entered any recent ranking — covered by five fallback layers: ① sitemap enumeration (must be reached) ② the historical-rank full ranking ③ the `/o` owner index ④ category detail pagination ⑤ the repo related hub.

## 11. Preview-environment noindex (a hard constraint for production / test domains)

> Background: production and test are merged in the same Vercel project, and the test domain points at a Preview deployment (deploy topology / domains see [OPS.md](./OPS.md)). SEO hard constraint: the test environment must stay private/noindex.

**Actual implementation: the single environment variable `SITE_INDEXABLE` controls all three SEO silence defenses** (not decided by host):

| Defense | Implementation |
|---|---|
| **robots.txt bans crawling site-wide** | `SITE_INDEXABLE !== "1"` → `app/robots.ts` returns `User-Agent: *` + `Disallow: /` (see §5) |
| **Per-page meta `noindex`** | The same flag drives the root layout's `robots: { index: indexable, follow: indexable }`, covering the whole site; when unset, every page is `<meta name="robots" content="noindex,nofollow">` |
| **The sitemap is not published outward** | When `Disallow: /`, also do not write a `Sitemap:` line into robots, further lowering the chance of being discovered (the sitemap route itself is still reachable, but robots does not advertise it) |
| **Preview stays PRIVATE** | The Vercel project's preview deployments are set non-public (Deployment Protection), so anonymous crawlers cannot reach them at the source |
| **canonical does not leak** | Preview's `NEXT_PUBLIC_SITE_URL` still points at the production domain ⇒ even if meta is emitted by mistake, canonical still points at production and does not let `*.vercel.app` / `pre.gitstarclub.com` become the canonical URL |

Code (`web/app/_shell/RootShell.tsx`):

```ts
const indexable = process.env.SITE_INDEXABLE === "1";
export const metadata: Metadata = {
  // ...
  robots: { index: indexable, follow: indexable },
};
```

**Why not host detection**: the early design wanted `isProductionHost()` (host / `VERCEL_ENV`) to decide automatically, but around launch the teaser and the web app share the production domain during a transition, and a host decision can easily flip open when it should not; an env flag is explicit, controllable, and a single flip point.

- **Flip on launch day**: ① add `SITE_INDEXABLE=1` in the Vercel project's production environment ② redeploy (no code change needed) ③ robots returns to `Allow: /` + the meta `noindex` disappears + the sitemap is advertised in robots.
- **Cutover-day checklist**: after the alias is switched to the web app and the `SITE_INDEXABLE=1` deploy has finished, confirm ① `/robots.txt` returns `Allow: /` + a `Sitemap:` line ② no page's `<meta name="robots">` still contains `noindex` ③ `/sitemap.xml` is reachable ④ the teaser is retired and its deployment no longer holds the production domain (avoid two deployments fighting over the domain).
- **Never** submit a preview URL / sitemap to Search Console during the preview period.
- **Risk**: if a half-finished product is indexed, it pollutes brand terms and creates duplicate content, and after the production cutover a large "remove outdated URLs" cleanup is required — prevention costs far less than remediation.

## 12. Performance is SEO (Core Web Vitals as a ranking factor)

> Content pages are `○` static / `●` on-demand ISR (route-locale server-side localized HTML, see [FRONTEND.md](./FRONTEND.md) §2.5); TTFB / cache are pure static / ISR hits; the body has zero client JS, and the HTML size is kept within the threshold.

SSG + zero client JS + HTML < 20KB naturally satisfies them (see the performance strategy in [ARCHITECTURE.md](./ARCHITECTURE.md) + the user's web/performance rules):

| Metric | Target | How this site achieves it |
|---|---|---|
| **LCP** | < 1.5s (better than Google's "good" 2.5s threshold) | Static HTML goes through the Edge CDN + the hero font is preloaded; no client-JS render blocking |
| **CLS** | < 0.05 | Chart SVG sizes are fixed (`width`/`height` explicit), and font metrics are overridden (avoid FOUT shift) |
| **INP** | Extremely low / near 0 | Content pages have almost no JS and no long tasks |
| **FCP** | < 1.0s | Critical CSS is inlined, and fonts are subsetted woff2 (the Plus Jakarta Sans subset is ~30KB) |
| **TTFB** | Low | 99.99% hit the edge cache; an ISR cold start only reads KB of JSON (see §3) |

- **Images**: OG images are drawn live by the `next/og` route and cached by ISR / CDN (see §13), and after a hit they do not consume Function again; if a page has images, they always have an explicit size + `loading=lazy` (below-fold).
- **Fonts**: at most two families (Plus Jakarta Sans + Geist Mono), `font-display: swap`, subsetted; preload only the body Plus Jakarta, and load Geist Mono later.
- **Cache headers**: historical pages use `Cache-Control: s-maxage=86400, stale-while-revalidate` (see ARCHITECTURE).
- **Mobile-first indexing**: Google indexes the mobile version — SSG is responsive, with no mobile-specific blocking; ensure the mobile viewport meta (injected by Next.js by default) and touch reachability.

> CWV is a **real ranking factor** (Page Experience), and this site's zero-JS architecture makes hitting the bar almost "free" — this is a structural advantage over dynamic-dashboard competitors and should be maintained as a moat beyond content relevance (keep monitoring with Speed Insights, see [ARCHITECTURE.md](./ARCHITECTURE.md)).

## 13. OG / social cards (graphite gray + star gold)

**Generation and storage** (see [ARCHITECTURE.md](./ARCHITECTURE.md) / [OPS.md](./OPS.md)):
