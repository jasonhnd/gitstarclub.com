# gitstarclub v0.2 设计（叙事与发现）

> 本文是 v0.2 的**设计蓝图**（设计→定稿→再写代码）。v0.1 MVP 已完整上线并自动化（Vercel-only 数据生命周期 Phase 2–5、静态 + 客户端 i18n、监控、测试套件）。v0.2 的主题是**叙事与发现**：让用户更容易"找到"和"读懂"开源编年史。
>
> 关联：[ARCHITECTURE.md](./ARCHITECTURE.md) · [PRODUCT.md](./PRODUCT.md) · [VERCEL-DATA-OPERATIONS.md](./VERCEL-DATA-OPERATIONS.md) · [RANKING.md](./RANKING.md)。

## 0. 边界：v0.2（无 DB）vs v0.3（必须先上 DB）

v0.1 的核心约束**继续保持**：运行时纯静态只读 JSON / Blob、零运行时引擎/数据库、Vercel-first 统一计费、零本地 recurring 依赖。

| 能力 | 阶段 | 为什么 |
|---|---|---|
| 全站搜索（≥10k repo） | **v0.2** | 数据小（5,261 repo），可建静态索引，客户端检索，零后端 |
| LLM 月度叙事 | **v0.2** | Vercel AI Gateway 生成、产物落 Blob JSON，仍是静态读路径 |
| 拐点检测与标注 | **v0.2** | 纯算法，跑在现有 recompute 里，零新数据源 |
| 可分享卡片 | **v0.2（部分已做）** | OG 图机制已具备（每页 og:image 已修），补每周期卡片 + 分享按钮 |
| **≥100 star 下钻（46 万 repo）** | **v0.3，阻塞** | 46 万 repo × 历史 = JSON shard 扛不住，**必须引入分析型 DB（ClickHouse 系）**——见 §5，需架构决策（且与「Vercel-first 零外部账单」有张力） |
| 多 repo 对比页 | **v0.2 简版 / v0.3 完整** | 简版（对比已有 ≥10k repo 的曲线）可 v0.2；任意 repo 对比需 v0.3 DB |
| 主题/语言聚类、语义检索 | **v0.3** | 需 embedding + 向量库（Turbopuffer/Neon），新数据层 |

**结论**：v0.2 做 **搜索 / LLM 叙事 / 拐点 / 分享卡片 / 对比简版**，全部不碰 DB、不破坏静态模型。下钻与语义检索留 v0.3，且需要你先拍板 DB 选型（§5）。

---

## 1. 全站搜索（最高优先级）

**目标**：导航栏一个搜索框，输入 repo 名 / owner / 关键词 → 即时结果 → 点进 repo/org 页。

**技术决策**：**客户端检索 + 构建期静态索引**，不引后端。
- 候选：Pagefind（索引渲染后的 HTML）vs Orama/MiniSearch（索引结构化 JSON）。
- **选 Orama 或 MiniSearch（索引 JSON）**，不选 Pagefind——因为 repo 页是按需 ISR、构建期并未全部预渲染，Pagefind 抓不到；而我们本就有结构化数据。
- **新增 `search/index.json`**：recompute 阶段从 repos shard 派生（`{id, full_name, owner, language, current_stars, description}`，5,261 条 ≈ 0.5–1MB gzip 更小），落 Blob、走 CDN。
- 客户端：一个 `"use client"` 搜索组件，首次聚焦时懒加载 `search/index.json` + 建 MiniSearch 索引（5k 条建索引 < 50ms），输入即时过滤（typo 容错 + 按 stars 加权排序），结果链到 `/<owner>/<name>`。
- **零运行时后端、零额外账单**；索引随每次 recompute 刷新（自动含新晋 repo）。

**落地**：① recompute 加 `search/index.json` 产物 + 契约；② `SearchBox` 客户端组件（懒加载 + MiniSearch）；③ 接进 `Chrome` 导航。**工作量：小。建议第一个做。**

## 2. LLM 月度叙事

**目标**：每月榜页顶部一段自动生成的中英文叙事（"2026 年 6 月，X 因 Y 爆发式增长……"），让数字有故事。

**技术决策**：**Vercel AI Gateway**（Vercel-first，不开外部账单）+ 便宜模型（Claude Haiku / 4o-mini）。
- **L3 workflow 新增 step `generateNarrative`**：对**刚收口**的月，取该月 top movers / 新晋 / 增速作为 context，调 AI Gateway 生成 ~80 字叙事，中英各一，落 `narrative/<period>.json`（Blob）。幂等（已存在则跳过，除非强制重算）。
- 读侧：月榜页读 `narrative/<period>.json`（带扁平回退，无则不渲染）。
- **成本**：每月一次、~$0.001/篇 × 12/年 ≈ 可忽略；只对收口月生成，不碰当前月。
- 质量闸门：叙事是"锦上添花"，生成失败不阻塞发布（best-effort，复用告警）。

**落地**：① `narrative/<period>.json` 契约；② workflow step（AI Gateway 调用 + 落 Blob）；③ 月榜页渲染。**工作量：中（含 prompt 调试）。**

## 3. 拐点检测与标注

**目标**：在 repo 的 star 曲线上自动标出"何时爆发"的拐点。

**技术决策**：**纯算法，跑在 recompute 里**，零新数据源、零 LLM。
- 对每个 repo 的月度 flow 序列做简单 changepoint：标出 flow 相对其滚动基线显著跃升的月份（如 flow > k × 前 N 月中位数，或最大单月相对增幅）。
- 写进 `entity/repo/<id>.json` 的新字段 `inflections: [{period, flow, kind}]`。
- 读侧：`StarCurve` 在这些月画标记 + tooltip。

**落地**：① recompute entity 加拐点计算（纯函数，带单测）；② 契约加 `inflections`；③ StarCurve 渲染标记。**工作量：小–中。**

## 4. 可分享卡片（部分已做）

**现状**：每页 og:image 已修（repo 页自定义卡、其余站点卡）。
**补**：① 每月/每年榜的 OG 卡（`app/rankings/[year]/[period]/opengraph-image.tsx`，动态生成"6 月榜 top3"卡）；② 页面上一个"分享"按钮（复制链接 / X 分享 intent）。**工作量：小。**

## 5. v0.3 阻塞点：≥100 star 下钻需要 DB 决策（需你拍板）

下钻到 ≥100 star（46 万 repo）、多 repo 任意对比、主题聚类、语义检索——**都装不进当前 JSON shard 模型**（46 万 × 历史太大，且需要任意筛选/聚合/向量查询）。必须引入新数据层，这与「Vercel-first、零外部账单、运行时零引擎」**有直接张力**，需要一次架构决策：

| 选项 | 说明 | 张力 |
|---|---|---|
| **Tinybird（托管 ClickHouse）** | 分析查询强、roadmap 既定选项 | 外部账单（违反"零散落账单"）；运行时要查它（违反"纯静态"）——需重新界定 |
| **Vercel Postgres / Neon** | Vercel 生态内 | 关系库扛分析型聚合（46 万 × 时序）吃力 |
| **继续 JSON + 预算更多视图** | 不引 DB | 46 万 repo 的任意筛选/对比组合爆炸，预算不出来 |
| **ClickHouse 自建 / 公共实例** | 便宜 | 运维成本、可靠性（架构文档已评估过不可行） |

**建议**：v0.2 先不碰下钻；v0.3 启动前**专门过一次这个决策**（我可以做选型对比 + POC）。在决策前，下钻/语义检索保持"未实现"。

---

## 6. 建议建造顺序（v0.2）

1. **搜索**（小、最高用户价值、零后端）→ 先做。
2. **拐点**（小、纯算法、增强 repo 页叙事）。
3. **分享卡片补全**（小、OG 机制已具备）。
4. **LLM 月度叙事**（中、需 AI Gateway 接入 + prompt 调试）。
5. （v0.3 闸门）DB 选型决策 → 下钻 / 对比 / 聚类。

每项都遵循 v0.1 的纪律：先离线/合成验证正确性，再上；产物落 Blob、读侧带回退；workflow step 幂等 + best-effort。
