# Server-Side Per-Locale Rendering Design

## Decision

GitStarClub should move i18n from cookie-driven client preference to deterministic, server-rendered locale URLs.

Recommended approach:

- Keep English as the default locale on the existing unprefixed URLs: `/`, `/rankings`, `/compare`, `/facebook/react`.
- Add locale-prefixed URLs for every non-default locale: `/ja`, `/zh/rankings`, `/zh-TW/compare`, `/fr/facebook/react`.
- Render the page from the route segment, not from a cookie: `params.locale -> getDictionary(locale) -> server HTML`.
- Prebuild only the hot/core localized surface at deploy time. Keep historical, category, repo, and org long tail on ISR/on-demand generation.
- Emit per-locale canonical URLs, `hreflang` alternates, and per-locale sitemap entries.
- Keep client JavaScript near zero by removing client dictionary swaps from content pages. Client islands receive already-localized labels as props.

This gives every supported locale an indexable URL without multiplying deploy-time static generation by seven.

Supported locales remain the existing dictionary set:

| Locale | URL segment | HTML `lang` / `hreflang` |
|---|---:|---:|
| English | none | `en` |
| Japanese | `ja` | `ja` |
| Simplified Chinese | `zh` | `zh-CN` |
| Traditional Chinese | `zh-TW` | `zh-TW` |
| Korean | `ko` | `ko` |
| Spanish | `es` | `es` |
| French | `fr` | `fr` |

## Current State

The current implementation is intentionally static, but it is static English:

- `web/lib/i18n/index.ts` defines seven locales and `getDictionary(locale)`.
- `web/lib/i18n/client.tsx` imports `en` directly. `chromeText()` and `<T>` always resolve the English dictionary.
- `web/lib/i18n/client-runtime.tsx` is a client provider that reads `gsc_lang`, lazy-loads dictionaries, and powers `useChrome()`.
- `web/lib/i18n/server.ts` is deprecated because reading cookies from pages forces dynamic rendering.
- `LanguageSwitcher` writes `gsc_lang` in the browser and dispatches a client event; it does not navigate to a localized URL.
- `/api/lang` sets `gsc_lang` and redirects to a safe internal path.
- `layout.tsx` renders `<html lang="en">`, then `LANG_INIT_SCRIPT` may change `documentElement.lang` on the client.
- `Chrome`, `Footer`, `Breadcrumbs`, `rankings/page.tsx`, and most content pages use static English dictionaries or `T`.
- `/compare` is the exception: the interactive client tool is wrapped in `I18nProvider`, but the page shell, metadata, JSON-LD, FAQ, and server-rendered content are still English.
- `web/app/sitemap.ts` emits one language-neutral URL list. `web/lib/seo.ts` intentionally emits no `hreflang`.

That design preserves SSG/ISR, but non-English content is not present in server HTML and non-English URLs do not exist.

## URL Scheme

Use path-prefix locale routing.

| Logical page | English canonical | Japanese canonical | French canonical |
|---|---|---|---|
| Home | `/` | `/ja` | `/fr` |
| Rankings | `/rankings` | `/ja/rankings` | `/fr/rankings` |
| Month ranking | `/rankings/2026/7` | `/ja/rankings/2026/7` | `/fr/rankings/2026/7` |
| Category | `/categories/language/typescript` | `/ja/categories/language/typescript` | `/fr/categories/language/typescript` |
| Repo | `/facebook/react` | `/ja/facebook/react` | `/fr/facebook/react` |
| Org | `/o/vercel` | `/ja/o/vercel` | `/fr/o/vercel` |

Rules:

- English keeps the current unprefixed URLs. This preserves existing links, canonical history, GitHub-style repo URLs, and current sitemap semantics.
- `/en` and `/en/*` are not canonical. They should 308 redirect to the matching unprefixed URL.
- Non-default locale prefixes are canonical for those locales.
- Trailing slash behavior should stay unchanged: no new trailing slash convention.
- Locale prefixes are reserved only when the first segment exactly matches a supported locale. Localized repo URLs use three segments, for example `/ja/facebook/react`, so normal two-segment repo URLs like `/ja/some-repo` can still be interpreted as an English repo route unless the second segment is a reserved localized top-level route.
- Unsupported locale-looking prefixes should not be guessed. `/pt/rankings` should 404 or resolve through the normal route tree, not silently fall back to English.

All internal links must be generated through a helper such as:

```ts
localizedPath("en", "/rankings")       // "/rankings"
localizedPath("ja", "/rankings")       // "/ja/rankings"
localizedPath("zh-TW", "/")            // "/zh-TW"
stripLocale("/fr/facebook/react")      // { locale: "fr", path: "/facebook/react" }
```

Do not hand-concatenate locale prefixes in page components.

## Canonical And Hreflang

Every localized page should canonicalize to itself.

For `/rankings` in English:

- Canonical: `https://gitstarclub.com/rankings`
- `hreflang=en`: `https://gitstarclub.com/rankings`
- `hreflang=ja`: `https://gitstarclub.com/ja/rankings`
- `hreflang=zh-CN`: `https://gitstarclub.com/zh/rankings`
- `hreflang=zh-TW`: `https://gitstarclub.com/zh-TW/rankings`
- `hreflang=ko`: `https://gitstarclub.com/ko/rankings`
- `hreflang=es`: `https://gitstarclub.com/es/rankings`
- `hreflang=fr`: `https://gitstarclub.com/fr/rankings`
- `hreflang=x-default`: `https://gitstarclub.com/rankings`

For `/ja/rankings`:

- Canonical: `https://gitstarclub.com/ja/rankings`
- Same alternate set as above.

`pageMeta()` should become locale-aware:

- Input: `locale`, canonical path without locale, localized title, localized description, and whether this page participates in localized SEO.
- Output: localized canonical URL, Open Graph URL, Open Graph locale, Twitter metadata, and `alternates.languages`.
- `x-default` should always point at the English unprefixed URL.
- Existing relative `path` callers should migrate to canonical path inputs. The helper, not each page, owns locale prefixing.

Repo names, org logins, programming language names, GitHub topics, repository descriptions, and numeric data remain data, not translation keys.

## Rendering And Scale

The issue's sitemap count is about 10,877 canonical URLs. Multiplying by seven locales yields about 76,139 locale URLs.

### Rejected: Full SSG For All Locale URLs

Full SSG means every deploy generates about 76k pages.

Planning estimate:

| Item | Estimate |
|---|---:|
| URLs | 10,877 x 7 = 76,139 |
| Average static generation time | 250-750 ms per page |
| Serial generation CPU | 5.3-15.9 hours |
| Average prerendered HTML/RSC/metadata output | 40-120 KB per page |
| Deployment output | 3.0-9.1 GB |

Even with build parallelism, this is the wrong default. It makes every deploy pay for cold long-tail pages in every language, including repo/org pages that may never be visited. It also makes Vercel build output and upload size grow with the tracked GitHub dataset.

### Rejected: Cookie-Based Server Rendering

Reading `gsc_lang` through `cookies()` in pages or layouts would make routes dynamic. That repeats the problem already documented in `web/lib/i18n/server.ts`: the route becomes per-request SSR and loses the static/ISR cache model. It also creates a canonical ambiguity because the same URL can produce different languages.

### Rejected: Selective English-Only Long Tail

Selective localization of only home, rankings, categories, about, and compare would keep sitemap size closer to roughly 35k URLs if repo/org pages stayed English-only.

That is attractive operationally, but it has three product and SEO problems:

- The language switcher becomes inconsistent on the pages users most often reach from search: repo and org detail pages.
- Repo/org FAQ, chrome, JSON-LD names, table captions, and explanatory copy remain English even when the user selected another locale.
- A future move from English-only long tail to localized long tail would require changing canonicals, sitemap shape, and hreflang behavior later.

Selective localization should remain a rollback lever if telemetry shows crawl pressure is too high, not the launch architecture.

### Recommended: Full Locale URL Coverage With ISR Long Tail

Use full locale URL coverage, but do not full-SSG it.

| Page group | Locale URLs | Deploy prebuild | Runtime mode |
|---|---:|---|---|
| Home, pulse, rankings index, compare, about, privacy | all 7 | yes | static |
| Current year/month/week ranking pages | all 7 | yes | static/ISR per existing route |
| Historical year/month/week ranking pages | all 7 | no, except current static params | on-demand ISR |
| Category index and dimension pages | all 7 | yes for bounded index/dimensions | ISR where registry-driven |
| Category detail and pagination pages | all 7 | no full cross-product | on-demand ISR |
| Org index pages | all 7 | first page yes; deeper pages ISR | ISR |
| Repo detail pages | all 7 | no | on-demand ISR, current 86400-second behavior |
| Org detail pages | all 7 | no | on-demand ISR and cron/path invalidation behavior |

This keeps deploy work close to the current build plus a small locale multiplier for hot pages. The eventual cache can still grow toward the 76k-page range if crawlers and users visit everything, but that growth is amortized over real demand instead of forced into every deploy.

Planning estimate:

| Item | Estimate |
|---|---:|
| Sitemap URLs | about 76,139 |
| Sitemap files | 7 locale sitemaps of about 10,877 URLs each, plus a sitemap index |
| Deploy-time localized pages | roughly 70-250, depending on current-period and category-index static params |
| Incremental deploy generation | usually under 2 minutes if long-tail static params stay empty or bounded |
| Eventual ISR cache if fully crawled | roughly 3-9 GB, generated over time rather than uploaded on every deploy |
| Cold generation for long-tail crawl | expected over days or weeks; each page must do bounded Blob reads only |

The key requirement is to keep `generateStaticParams()` bounded. Do not cross-product all repos, orgs, categories, periods, and locales at deploy time.

## Middleware

Add `web/middleware.ts` for URL normalization and preference redirects only. It must not be part of rendering data flow.

Responsibilities:

1. Ignore non-page requests: `/_next/*`, static assets, `favicon.*`, `robots.txt`, `sitemap*`, `opengraph-image`, `/api/*`, `/search-index`, `/repo-curve`.
2. If the first segment is `en`, 308 redirect to the unprefixed URL.
3. If the first segment is a supported non-default locale, let the request continue. Explicit locale URLs always win over cookie or header preference.
4. If the path is unprefixed and the `gsc_lang` cookie is a supported non-default locale, 307 redirect to the matching prefixed URL.
5. If the path is `/`, no locale cookie exists, and `Accept-Language` best-matches a supported non-default locale, 307 redirect to that locale root. Do not apply Accept-Language redirects to all deep links; shared unprefixed canonical URLs should stay predictable.
6. Do not redirect prefetches or non-document requests.

The cookie remains useful as a navigation preference, but pages must not read it. Locale is determined by URL only once rendering starts.

Redirect examples:

| Request | Cookie/header | Result |
|---|---|---|
| `/en/rankings` | any | 308 `/rankings` |
| `/rankings` | `gsc_lang=ja` | 307 `/ja/rankings` |
| `/` | `Accept-Language: ko,...`, no cookie | 307 `/ko` |
| `/facebook/react` | no cookie | render English repo page |
| `/ja/facebook/react` | any cookie | render Japanese repo page |

`/api/lang` can remain as a compatibility endpoint, but it should redirect to the locale URL. For example, `GET /api/lang?lang=fr&next=/rankings` should set `gsc_lang=fr` and redirect to `/fr/rankings`, not back to `/rankings` for a client-side swap.

## Server Rendering Flow

Pages should receive locale from the route shape:

- Unprefixed route: `locale = DEFAULT_LOCALE`.
- Prefixed route: validate `params.locale` with `isLocale()` and reject `en` because middleware should strip it.

Rendering flow:

1. Parse and validate params.
2. Resolve `{ locale, canonicalPath }`.
3. Load `const t = await getDictionary(locale)`.
4. Read data through existing `@/lib/data` helpers.
5. Render all chrome, metadata, JSON-LD, FAQ, captions, and deterministic narrative in that locale.
6. Keep route segment config static. Do not call `cookies()` or `headers()` from pages or layouts.

The implementation should avoid duplicating page logic. Recommended structure:

```txt
web/app/rankings/page.tsx              -> calls RankingsPageView({ locale: "en" })
web/app/[locale]/rankings/page.tsx     -> validates params.locale, calls same view
web/app/_localized/rankings.tsx        -> shared server page implementation
```

The same pattern applies to dynamic pages:

```txt
web/app/[owner]/[name]/page.tsx
web/app/[locale]/[owner]/[name]/page.tsx
web/app/_localized/repo-page.tsx
```

`Chrome`, `Footer`, `Breadcrumbs`, `FaqBlock`, table captions, and page-specific components should accept `locale`, `t`, and `canonicalPath` or receive already-localized strings. They should not import `en` directly.

## Migrating Away From Static-English `T`

`T` currently hides the main problem because it looks localized but resolves English through `chromeText(en)`. It should not be used by server-rendered content pages after the migration.

Migration rules:

- Replace `<T path="rankings.title" />` with `t.rankings.title` or a server helper that resolves against the page dictionary.
- Replace `const LOC = DEFAULT_LOCALE` with the actual route locale.
- Replace `locale: "en"` in `pageMeta()`, JSON-LD builders, `FaqBlock`, and `RankingList` with the route locale.
- Move hardcoded UI strings into dictionaries before localizing a page. Examples found in current pages include `All-time`, `Complete ranking`, `Explore related pages`, `Organizations`, `Server-rendered comparison`, table captions, pagination labels, and source labels.
- Keep data labels as data. Do not translate repo names, org names, GitHub descriptions, license names, topics, or programming language names unless a separate normalized translation table exists.
- Update deterministic copy generators such as `geo-capsules`, `geo-faq`, `shareable-snippets`, and `narrative` to accept `locale` and return one server-selected string set. Do not render hidden paragraphs for all locales as the final SEO path.
- Expand formatting helpers so all seven locales use explicit Intl tags. The current `format.ts` only special-cases `en`, `ja`, and `zh`.

`web/lib/i18n/client-runtime.tsx` should become an interactive-tool fallback, not a content-page dependency. `/compare` should pass localized labels into `CompareClient` as props where practical. If a client provider remains for the compare tool, it must be initialized from the route locale and server dictionary, not from `document.cookie`.

## Language Switcher

The switcher should navigate, not mutate text in place.

Recommended behavior:

- Render each locale as a normal link to the corresponding locale URL.
- The active locale comes from the route, not from `document.cookie`.
- Selecting English from `/ja/rankings` navigates to `/rankings`.
- Selecting Japanese from `/rankings` navigates to `/ja/rankings`.
- Selecting French from `/ja/facebook/react` navigates to `/fr/facebook/react`.
- The switcher should not import dictionaries or dispatch `gsc:localechange`.
- The switcher should not be responsible for translating the current page. Navigation performs a server round trip and returns localized HTML.

Because current pages import `Chrome` directly, the lowest-JS implementation is to pass `locale` and `canonicalPath` into `Chrome`, then into `LanguageSwitcher`. If that churn is too high for the first implementation, a tiny `usePathname()` switcher island is acceptable temporarily, but it must only build links. It must not lazy-load dictionaries or rewrite DOM language.

## SEO And Sitemap

The sitemap should enumerate locale URLs, not only alternates.

Recommended sitemap shape:

- `/sitemap.xml` is a sitemap index.
- `/sitemap-en.xml` lists English unprefixed URLs.
- `/sitemap-ja.xml`, `/sitemap-zh.xml`, `/sitemap-zh-TW.xml`, `/sitemap-ko.xml`, `/sitemap-es.xml`, and `/sitemap-fr.xml` list prefixed URLs.
- Each URL entry includes the full alternate set, including itself and `x-default`.
- Each locale sitemap stays around 10,877 URLs, below the 50k URL limit.
- Last-modified, change-frequency, and priority should continue to use the deterministic helpers in `web/lib/sitemap.ts`. Do not introduce `new Date()` churn.

If Next's sitemap metadata route cannot serialize the required `xhtml:link` alternates for this project version, replace `app/sitemap.ts` with explicit XML route handlers. The output XML is the contract; the framework helper is an implementation detail.

Example entry for `/ja/rankings`:

```xml
<url>
  <loc>https://gitstarclub.com/ja/rankings</loc>
  <xhtml:link rel="alternate" hreflang="x-default" href="https://gitstarclub.com/rankings" />
  <xhtml:link rel="alternate" hreflang="en" href="https://gitstarclub.com/rankings" />
  <xhtml:link rel="alternate" hreflang="ja" href="https://gitstarclub.com/ja/rankings" />
  <xhtml:link rel="alternate" hreflang="zh-CN" href="https://gitstarclub.com/zh/rankings" />
  <xhtml:link rel="alternate" hreflang="zh-TW" href="https://gitstarclub.com/zh-TW/rankings" />
  <xhtml:link rel="alternate" hreflang="ko" href="https://gitstarclub.com/ko/rankings" />
  <xhtml:link rel="alternate" hreflang="es" href="https://gitstarclub.com/es/rankings" />
  <xhtml:link rel="alternate" hreflang="fr" href="https://gitstarclub.com/fr/rankings" />
</url>
```

Structured data must use the localized URL and `inLanguage` where the builder supports it. Visible breadcrumbs and `BreadcrumbList` names should be localized for chrome labels, while repo/org/category data labels remain unchanged.

## Route And Build Constraints

Keep the current static/ISR architecture:

- Do not read cookies in pages, layouts, metadata, or JSON-LD generation.
- Keep segment config exports as static literals.
- Keep repo and org `generateStaticParams()` empty for every locale.
- Keep historical ranking `dynamicParams = true`.
- Keep category detail pages bounded. Do not cross-product every public category, every pagination page, and every locale unless build telemetry proves it is safe.
- Keep preview deployments globally `noindex` through the existing `SITE_INDEXABLE` model.
- Keep data reads through existing Blob JSON view helpers. The i18n migration must not add workflow or data-pipeline coupling to page render.

Localized route implementation must be tested with Vercel builds, not only a local dev server, because static route classification is the main risk.

## Rollout Plan

1. Add route helpers and tests.
   - Implement locale parsing, `localizedPath()`, `stripLocale()`, BCP-47 mapping, Open Graph locale mapping, and route classification.
   - Test default-locale stripping, non-default prefixing, root path behavior, repo paths, org paths, and `zh-TW`.

2. Update metadata and sitemap infrastructure.
   - Make `pageMeta()` locale-aware.
   - Add alternates and per-locale canonical generation.
   - Split sitemap output by locale and verify XML alternates.

3. Add middleware.
   - Normalize `/en/*`.
   - Redirect cookie-selected unprefixed page requests to prefixed routes.
   - Use Accept-Language only for `/` when no cookie exists.
   - Exclude APIs, assets, metadata files, and prefetch/non-document requests.

4. Convert shell components.
   - Change `Chrome`, `Footer`, `Breadcrumbs`, and `LanguageSwitcher` to route-locale inputs.
   - Remove `LANG_INIT_SCRIPT` after route-locale rendering is complete.
   - Keep `gsc_lang` only as middleware preference, not rendering state.

5. Migrate core pages first.
   - Home, pulse, rankings index, compare, about, privacy.
   - Replace `<T>`, direct `en` imports, `DEFAULT_LOCALE` constants, and hardcoded English UI strings.
   - Verify server HTML contains non-English text for `/ja`, `/zh`, `/ko`, `/es`, and `/fr`.

6. Migrate ranking and category pages.
   - Year, month, week, category index, dimensions, details, and pagination.
   - Convert deterministic narrative to render only the active locale.
   - Keep ISR behavior bounded.

7. Migrate repo and org pages.
   - Add locale-prefixed ISR wrappers for repo and org detail pages.
   - Localize chrome, FAQ, captions, metadata, JSON-LD language, and explanatory labels.
   - Keep repo descriptions, names, topics, licenses, and language names as source data.

8. Convert client islands.
   - `CompareClient`, `SearchBox`, share controls, and pagination should receive localized labels as props.
   - Remove dictionary lazy-loading from content page paths.
   - Keep client JavaScript limited to true interactivity.

9. Update existing docs that currently say language is cookie-only and URL-neutral.
   - `docs/SEO.md` and `docs/FRONTEND.md` currently document the old design.
   - They should be updated in the implementation PR so docs do not contradict the shipped behavior.

10. Validate on Vercel preview.
    - `bun run build` must classify content routes as static or ISR, not dynamic SSR.
    - Inspect representative HTML for `/ja/rankings`, `/fr/rankings/2026/7`, `/ko/categories`, and `/zh-TW/facebook/react`.
    - Verify `/en/*` redirects.
    - Verify sitemap index and locale sitemap counts.
    - Verify canonical and `hreflang` tags in page HTML.
    - Keep `SITE_INDEXABLE` off until production launch.

11. Launch and monitor.
    - Ship with English unprefixed URLs unchanged.
    - Submit the sitemap index after production is indexable.
    - Monitor crawl errors, duplicate canonical reports, discovered-not-indexed pages, and ISR cold-render latency.
    - If long-tail localized repo/org crawl pressure is too high, use the selective-localization fallback by removing repo/org locale entries from sitemaps while keeping the routes functional.
